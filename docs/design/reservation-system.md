## 1. 目的

ゼミの1on1（発表・相談）予約を、スプレッドシートの日付タブ運用から
「カレンダーで日付を選ぶ → 空き枠を予約する」Webアプリに置き換える。

## 2. ユーザー

- ログイン: **Google ログイン必須**（better-auth）
- 利用可能アカウント: `@stu.musashino-u.ac.jp`（学生）/ `@ds.musashino-u.ac.jp`（先生）。`@musashino-u.ac.jp` を含め、それ以外はログインできない（2026-11-14, Issue #27 で決定）
  - Google の `hd` パラメータはヒントに過ぎないため、**サーバー側でメールドメインを必ず検証する**
  - `@` より後ろを2ドメインと **完全一致** で比較する（末尾一致にしない）

| 役割 | できること |
|---|---|
| student（学生） | 予約・取消 / 自分の予約一覧と発表回数を見る / 表示名を変える |
| teacher（先生） | 全体連絡を書く（自分の分を編集・削除）/ 全員の発表回数を見る。予約はしない |
| admin（管理者） | student の機能すべて / 全体連絡の管理（全員分）/ 他人の予約の取消 / 管理画面 |

- 役割は、最初のログイン（アカウントの作成時）にドメインで決める。`@stu.` は `student`、`@ds.` は `teacher`（2026-11-14, Issue #27 で決定）
  - ドメインで決めるのは、先生が役割の変更を待つ間に予約などが入り、「予約を持った teacher」のような状態が起きるのを防ぐため（#8 の Codex レビューで指摘）
  - 2回目以降のログインでは決め直さない。手で admin にした人や、管理画面で役割を変えた人が元に戻らないようにするため
- 最初の admin は手作業で DB を更新して作る
  - admin にするのは、プロフィールを登録した後の人だけにする（運用で守る。2026-11-14, Issue #27 で決定）。未登録の人を admin にすると、登録したときの学年が下の決まり（`@stu.` の admin は学年あり、`@ds.` の admin は学年なし）と合わないことがある。たとえば、学年を付けて student にした `@ds.` の人を未登録のまま admin にすると、学年のある `@ds.` の admin になる。それでも、学年の無い admin は管理画面の役割変更（`GRADE_REQUIRED`）で、学年のある admin は学年更新で扱えるため、API では防がない
- 初回のプロフィール登録で、学年の有無が役割と合わなければ `400 VALIDATION_ERROR` にする（2026-11-14, Issue #27 で決定）
  - 学年が要るのは student と、`@stu.` の admin。学年を持たないのは teacher と、`@ds.` の admin（admin は学生のことも先生のこともあるため、ドメインで決める）
  - `400` にする理由：本人の役割とメールは `/api/me` で画面も知っていて、登録画面は API と同じ判定（`isGradeRequiredOnRegistration`）で学年の欄を出し分ける。そのため、下の例外を除けば、画面から正しく送れば通り、`400` になるのは画面を通さずに送った入力の誤りだけになる
  - 例外：登録画面を開いた後に、管理者がその人の役割を、学年が要るかどうかが変わるように変えた場合（例：student から teacher へ）。画面は古い判定のまま学年の欄を出す（または出さない）ため、送ると `400` になり、入力のやり直しを促す文言が出る。画面を開き直すまで通らない。学年が要るかどうかが変わらない変更（例：student から `@stu.` の admin へ）では、開いたままの画面から送っても通る
  - この文言は画面を開き直すよう伝えないため、どちらの向きでも本人には押し直しても通らない理由が分からない。学年の欄が出ていた場合は、学年を選んだのに「学年を選んでください」と出る。学年の欄が無かった場合は、学年が要ることが伝わらず、表示名の誤りとして出る（文言を変えるかは決めていない）
  - 例外があっても専用の `409` にしないのは、起きるのが「本人が登録画面を開いている間に、管理者がその人の役割を変える」ときだけで、まれなため。開き直せば通り、`400` のときは何も保存しないのでデータも壊れない
  - 管理者の役割変更の `409 GRADE_REQUIRED` との違い：どちらも古い画面から送ると起きる。管理者の役割変更は、ほかの管理者の変更と重なると起き、専用の `409` で一覧から学年を選び直すよう案内できるため `409` にした。登録のほうは上のとおりまれなため、専用の code を作らず `400` のままにした

### 公開範囲

| 情報 | 本人 | 他の学生 | 先生・管理者 |
|---|---|---|---|
| 予約者名・学年 | ○ | ○ | ○ |
| 発表回数 | ○ | × | ○（全員分） |

公開範囲の制御は **APIレスポンスで行う**（フロントで隠すだけにしない）。

### ログインの記録に保存するもの

`sessions` には、better-auth の標準どおり接続元の IP（`cf-connecting-ip`）と User-Agent を保存する（2026-10-22, Issue #2 で決定）。IP は回数制限で利用者を区別するためにも使う。

## 3. 課題

- 日付ごとにタブが増え続け、目的の日を探しにくい
- 人数が増え、同じセルへの同時書き込み・上書きが起こりうる
- スマホでのスプレッドシート編集は操作しづらい
- 「済」の判定がセル色（グレー）頼みで、手作業のミスが起きやすい

## 4. 機能

### MVP に含める

| # | 機能 | 誰が |
|---|---|---|
| 1 | Google ログイン（2ドメイン限定）＋ 初回プロフィール登録（表示名・学年。先生は表示名だけ） | 全員 |
| 2 | トップ：月カレンダー ＋ 今週の全体連絡 | 全員 |
| 3 | 日別の枠の表（スプシ風）→ 空き枠をクリック → 「予約しますか？」→ はい で確定 | student / admin |
| 4 | 自分の予約の確認・取消（マイページ / 日別の表の自分の名前から） | student / admin |
| 5 | マイページ：予約一覧・発表回数・表示名の変更（学年は変更不可）。teacher / admin は今日（または次の開催日）の予約者も見る | 全員 |
| 6 | 全体連絡の作成・編集・削除（本人の分。admin は全員分） | teacher / admin |
| 7 | 発表回数一覧（全員分） | teacher / admin |
| 8 | 管理画面：休止日の登録（理由つき） | admin |
| 9 | 管理画面：日ごとの枠の編集 | admin |
| 10 | 管理画面：利用者一覧・役割の変更 | admin |
| 11 | 管理画面：学年更新（毎年4月。B4・MIDS B4・M2 は進路を選ぶ） | admin |
| 12 | 自動処理：今日（Asia/Tokyo）以降の金曜を4回分生成 / 毎晩、過ぎた予約を「済」にする | – |

### MVP に含めない（優先順）

1. アカウント画面の研究内容・研究ステップ（中身が未定）
2. 予約ルールの制限（1日1枠まで など）
3. 通知・リマインド（メール / Slack）
4. スプレッドシートからのデータ移行

### スプシから引き継がないもの

相談内容・要望・先生からの連絡（予約ごと）・日ごとのメモ。
先生からの連絡は全体連絡にまとめ、相談内容・要望は別ドキュメントで管理する。

## 5. 画面構成

```
[ログイン] ──(初回のみ)──> [プロフィール登録]  表示名・学年（先生は表示名だけ）
     │                          │
     └────────────┬─────────────┘
                  ▼
[トップ]  /                   月カレンダー ＋ 今週の全体連絡（teacher / admin はここから書く）
  │ 日付をクリック（過去の日付も開ける）
  ▼
[日別の枠の表]  /days/:date    スプシ風の表（時限・開始・終了・予約者名）
  │ 空き枠をクリック                    自分の名前をクリック → 取消
  ▼
(ダイアログ)「13:30〜13:50 を予約しますか？」→ はい / いいえ

ヘッダーから:
├── [マイページ]  /me           表示名の変更・自分の予約一覧（取消）・発表回数
│                               teacher は今日の予約者、admin はタブ（今日の予約すべて・自分の予約・管理画面）
├── [発表回数一覧]  /stats      teacher / admin にだけボタンを表示
└── [管理画面]  /admin          admin にだけボタンを表示
      ├── 学年更新
      ├── 開催日の管理（休止・理由・枠の編集）
      └── 利用者の管理（役割の変更）
```

- 休止日はカレンダー上でグレー。PC ではカーソルを合わせると「休講日」と表示し、クリックで理由を表示する（スマホはタップで理由を表示）
- カレンダーの週の始まりは日曜 / 月曜から選べる（既定は日曜）。選んだものはその端末のブラウザに保存し、DB には持たない（2026-10-23, Issue #5 で決定）
- 日別の表には、発表枠・休憩・先生からの共有・なし をすべて行として並べる
- 確認ダイアログはブラウザ標準の `<dialog>` を使う
- 予約・取消のルール（2026-10-23, Issue #7 で決定）
  - 予約できるのは、開始時刻（日本時間）より前の枠だけ。当日でも開始時刻ちょうどからは予約できない
  - 本人が取り消せるのは、開始時刻より前で、まだ「済」になっていない予約だけ。admin は開始後の予約も「済」の予約も取り消せる
  - admin は日別の表で、全員の予約者名から取消できる（ダイアログには誰の予約かを出す）
  - 予約できない枠（発表以外・休止日・開始後）への予約は `409 SLOT_NOT_RESERVABLE`、埋まっている枠は `409 SLOT_TAKEN`、本人が取り消せない予約は `409 RESERVATION_NOT_CANCELABLE`
- マイページ（2026-10-29, Issue #8 で決定）
  - 予約一覧は「予約中」（日付の近い順）と「実施済み」（新しい順）に分ける
  - 開始時刻を過ぎた予約は、「済」になる前（当日、Cron の実行前）でも「実施済み」に入れる。発表回数は `done` の件数のため、反映は翌日になることを画面に添える（2026-10-29, Issue #8 のレビューで決定）
  - teacher は予約しないため、予約一覧と発表回数は出さない（API は teacher にも空の一覧と 0 を返す）。代わりに今日の予約者を出す（下の Issue #28 の項）
- teacher・admin のマイページ（2026-11-14, Issue #28 で決定）
  - 表示名の変更は、どの役割でも一番上（admin はタブより上）にいつも出す
  - teacher には、表示名の変更の下に「今日の予約者」（時刻・予約者名・学年）を出す。見るだけで、予約・取消はできない。各行から日別の表へ移れる
  - admin のマイページは「今日の予約すべて」「自分の予約」「管理画面」のタブに分ける。選んだタブは `/me?tab=today|mine|admin` で URL に持つ（再読み込みや、日別の表から戻ったときも同じタブを開くため）。`tab` が無い・知らない値なら「今日の予約すべて」を開く
    - 「今日の予約すべて」は teacher と同じ、見るだけの一覧。取消は日別の表で行う
    - 「自分の予約」は student と同じ予約一覧と発表回数
    - 「管理画面」は管理画面の各タブへのリンクを並べる（管理画面は `AdminLayout` の中で結果の文言などを共有して動くため、埋め込まない）
  - 出す日は、今日（日本時間）以降で一番近い開催日（`GET /api/days/next`）。今日が開催日なら、枠がすべて終わっても日付が変わるまでは今日を出す
  - 休止日は飛ばさない。一番近い開催日が休止日なら、「休講」と理由だけを出す（今日や次の開催日が休講だと分かるようにするため）
  - 今日以降に開催日が無いときは「予定されている開催日はありません」と出す
- ヘッダーには、アプリ名（トップへ）・マイページ・ログアウトを置く。ログインとプロフィール登録が要る画面（登録画面を除く）はすべて、親ルートでヘッダーとログイン確認を共有する（2026-10-29, Issue #8 で決定）。teacher / admin には、マイページの前に発表回数一覧も置く（2026-10-30, Issue #10 で決定）
- 全体連絡（2026-10-30, Issue #9 で決定）
  - 連絡は開催日ごとに書く（開催日は必須）。本文は 1〜1000 文字（絵文字1つ = 1文字）で、改行とタブは使える。タイトルは持たない
  - 表示期間：開始日が空なら作成日（日本時間）から、終了日が空なら開催日まで。編集しても作成日は変わらない（表示を始める日がずれないように）
  - 開始日と終了日の前後は、両方入っているときだけ API で確かめる（`400 VALIDATION_ERROR`。DB の CHECK 制約も同じ範囲）。空を補ったあとの期間で、これから表示される日が無い連絡は、画面で送らせない
  - 並び順は、表示を始める日の昇順。同じ日なら作成した順
  - 編集・削除できるのは、書いた本人と admin。書いた本人は、あとで役割が変わっても自分の分を直せる
  - 編集（PATCH）でも、すべての項目を送る（空の開始日・終了日は null）
  - 表示前の連絡はトップの一覧に出ないため、「表示前の連絡」として別に出す（teacher は自分の分、admin は全員分。`GET /api/announcements/upcoming`）。役割が変わった人は、自分の表示前の連絡が1件以上あるときだけ出す
  - トップの連絡欄はカレンダーの上に置き、書く・編集する入力欄は連絡欄の中で開く
  - 開催日の候補は、今日以降の開催日（休講日も「（休講）」を付けて選べる）を今月と来月の分から作る。Cron が4週分ずつ作るため2か月分で足りる。過去の開催日かどうかはサーバーでは確かめない
- 発表回数一覧（2026-10-30, Issue #10 で決定）
  - 載せるのは、予約できる役割（student / admin）で在籍中（`isEnrolled = true`）の、プロフィール登録済みの人。teacher と卒業生は載せない
  - 0 回の人も載せる（まだ発表していない人を見つけられるように）
  - 並び順は、学年（`GRADES` の順。学年の無い admin は最後）→ 表示名。表示名の順は DB の照合順序に従う（読みの50音順ではない）
  - 回数は `done` の件数。マイページと同じく、反映は翌日になることを画面に添える
  - student が URL を直接開いたときは、トップへ移さず「この画面は先生と管理者だけが見られます」と出す（なぜ見られないかが分かるように）
- 管理画面・休止日（2026-10-30, Issue #11 で決定）
  - 管理画面は `/admin` の下にタブで並べる（`/admin` を開くと最初のタブ「開催日の管理」`/admin/days` へ移す）。admin かどうかは親ルートで1回だけ確かめ、admin 以外にはタブも中の画面も出さず「この画面は管理者だけが見られます」と出す
  - 休止・再開できるのは、今日（日本時間）以降の金曜だけ。今日より前は `409 SEMINAR_DAY_PAST`（過去の記録を書き換えないため。実施した日を休止すると「済」の予約と発表回数が残ったまま休講と表示されて記録が食い違い、再開すると枠の無い過去の日に時間割の枠を作ってしまう）。金曜以外は `400 VALIDATION_ERROR`
  - 休止理由は任意（理由なしは `null` を送る）。1行・100文字まで（絵文字1つ = 1文字）で、表示名と同じく見えない文字・制御文字は使えない
  - 休止すると、その日の開始前の枠の予約を消す（枠は残す）。今日を休止するとき、開始時刻を過ぎた枠の予約は発表済みのため残し、翌日の Cron で「済」にする（消すと発表回数が減るため。2026-10-30, Issue #11 のレビューで決定）
  - 再開すると理由を `null` に戻し、枠が1つも無い日だけ時間割どおりの枠を作る
  - 行が無い日（4週間より先など）は、休止なら `closed` の行を（枠は作らない）、再開なら `open` の行と時間割どおりの枠を作る
  - 休止と同時に予約されても休止日の開始前の枠に予約が残らないよう、予約の INSERT は開催日の行に共有ロック（`FOR SHARE`）を掛ける
  - 開催日の管理の画面は、月ごとにその月の金曜をすべて並べる（行の無い日は「未作成」）。休止は理由の入力 → 確認ダイアログ（予約が消えることを書く）の順で、結果に消した予約の件数を出す。理由の変更も休止と同じ値を送るため、画面が古く、ほかの管理者が開催日に戻していた場合に備えて、確認ダイアログに予約が消えることを書く
- 管理画面・枠の編集（2026-10-31, Issue #12 で決定）
  - 変えられるのは種類・開始時刻・終了時刻の3つ。時限（`period`）は変えない。編集（PATCH）でも3つすべてを送る（全体連絡の編集と同じく、開始と終了の前後を API で確かめるため）
  - 時刻は `HH:MM`（00:00〜23:59）。開始は終了より前にする（`400 VALIDATION_ERROR`。DB の CHECK 制約も同じ条件）
  - 開始時刻が同じ日のほかの枠と同じなら `409 SLOT_START_TIME_TAKEN`。UNIQUE(seminarDayId, startTime) で防ぎ、時間帯の重なり（13:30〜13:50 と 13:40〜14:00 など）は確かめない
  - 開始時刻を過ぎた枠（今日より前の日の枠はすべて）は変えられない（`409 SLOT_STARTED`）。休止と同じく、発表済みの予約を消したり、過去の記録を書き換えたりしないため。休止日の枠は変えられる。編集で開始時刻を今より前に動かすことは確かめない
  - 画面で見ていた変更前の3項目（`previous`）も送り、今の枠と1つでも違えば変えない（`409 SLOT_CHANGED`）。3項目をすべて上書きするため、古い画面から保存すると、ほかの管理者の変更（休憩にした枠など）を黙って元に戻してしまうため（2026-10-31, Issue #12 のレビューで決定）。開始済みの枠は、変更前の値が違っていても `409 SLOT_STARTED` を返す（取り直しても変えられないため）
  - 種類を `presentation` から `presentation` 以外にすると、その枠の予約を消す（時刻だけの変更や、`presentation` 以外どうしの変更では消さない）。枠の更新と予約の削除は `db.batch` で送り、両方成功するか両方失敗するかのどちらかにする
  - 種類の変更と同時に予約されても `presentation` 以外の枠に予約が残らないよう、予約の INSERT は枠の行にも共有ロック（`FOR SHARE`）を掛ける
  - 編集の画面は `/admin/days/:date`（タブは「開催日の管理」のまま）。開催日の管理の一覧で、今日以降の行のある日に「枠を編集」を出す。枠の表示には `GET /api/days/:date` を使う
  - 種類を `presentation` から `presentation` 以外にするときは、予約の有無にかかわらず確認ダイアログに「予約があれば削除されます」と書く（画面を開いている間に予約が入っていても、注意を見ずに消さないため）。それ以外（時刻だけの変更など）は確かめずに送る。画面を開いている間にほかの管理者が種類を変えていても、変更前の値が合わずに何も変わらないため、確かめるかは画面の種類で決めてよい。結果に消した予約の件数を出す
- 管理画面・利用者と役割（2026-11-04, Issue #13 で決定）
  - 一覧には卒業生とプロフィール未登録の人も載せる。並び順は、在籍中 → 卒業生、学年（`GRADES` の順。学年の無い人は後ろ）、表示名（未登録の人は後ろ）、id
  - 変更後に在籍中（`isEnrolled = true`）の admin が1人も残らない変更は `409 LAST_ADMIN`。卒業生を数えないのは、大学のアカウントが消えるとログインできず、誰も管理画面に入れなくなるため。そのため、admin が卒業生だけのときはその人たちを外せない（先に在籍中の人を admin にする）。今の役割が admin でない人の変更には人数の条件を掛けない。ほかの admin がいれば、自分を外すこともできる
  - admin 全員と対象者の行を id の順に `FOR UPDATE` でロックしてから判定し、2人が同時に互いを外しても admin が0人にならないようにする
  - teacher にするときは、学年を `null` にし、本人が取り消せる状態の予約（開始前で `done` でないもの）を消す。teacher は学年を持たず予約もしないため。実施済みの記録と、開始後でまだ「済」になっていない予約は残す。すでに teacher の人に送っても同じ処理をする。teacher 以外への変更では予約を消さない
  - 学生は学年を必ず持つ。学年の無い人（teacher、学年の無い admin など）を student にするときは、学年も一緒に送る。送らなければ `409 GRADE_REQUIRED`（要るかどうかが今の学年で決まるため `400` にしない）。学年を保存するのは今の学年が空のときだけで、学年のある人に送っても今の学年のまま（学年の編集はこの API の役割ではなく、古い画面から上書きしないため）。student 以外には学年を送れない（`400`）。学年の無い在籍中の最後の admin を、学年を送らずに student にするときは `GRADE_REQUIRED` を先に返し、学年を付けて送ると `LAST_ADMIN` を返す（学年のある最後の admin は、学年を送らなくても `LAST_ADMIN`）
  - 登録時に「教員（学年なし）」を選んで student・学年なしになる経路は、#27 で塞いだ（登録 API が、役割ごとに学年の有無を確かめる）
  - teacher への変更と同時に予約されても開始前の予約が残らないよう、予約の INSERT は予約する人の行にも共有ロック（`FOR SHARE`）を掛け、役割を確かめる。すでに teacher なら `403 FORBIDDEN`
  - 未登録のまま teacher にされた人が初回登録で学年を送ると `400`（#27）。登録 API はセッションの役割で確かめるため、確かめた後に役割を変えられた場合に備えて、保存するときも行の役割で決め直す。teacher なら学年を `null` にし、それ以外で学年を送っていなければ今の学年を残す（teacher から student に変えるときに管理者が入れた学年を、`null` で上書きしないため）
  - 操作者が admin かは、入口に加えて、更新の処理の中（ロックを取った後）でも確かめる。入口を通ったあとに外された人が、処理中のリクエストで自分を admin に戻したり、ほかの admin を外したりできないようにするため。外されていれば `403 FORBIDDEN` を、ほかの理由より先に返す。権限そのものを変える操作のためで、ほかの管理操作（枠の編集・開催日の休止など）は入口だけで確かめる
  - 変更前の値の照合（#12 の `previous`）はしない。学年は空のときにしか保存しないため、ほかの項目を巻き戻す心配がない
  - 画面（`/admin/users`）は、セレクトで役割を選び「変更」を押すと確認ダイアログを出す。各行に今の役割を文字でも出す。学年の無い人に student を選ぶと学年のセレクトを出し、学年を選ぶまで「変更」を押せない。teacher にするときは、学年があれば消えることと、開始前の予約があれば削除されることを書く。自分を外すときは管理画面に入れなくなることを書き、成功後に自分の情報を取り直す。結果の文言は `AdminLayout` に出す（自分を外すとタブの画面が消えるため）。画面を移ると結果の文言を消す。保存された学年が送った学年と違うとき（画面が古く、すでに別の学年が入っていたとき）は、学年を変更していないことを結果に書く。teacher にしたときは、消した予約の件数を結果に出す
- 管理画面・学年更新（2026-11-06, Issue #14 で決定）
  - 年度は日本時間の暦年で数える（2027年4月の更新なら 2027）。実行できるのは日本時間の4月の間だけで、4月以外は `409 GRADE_PROMOTION_NOT_OPEN`。学年が正しい時期に実行すると全員が1つ上がり、画面から元に戻せないため。4月に実行し忘れたら、その年度は DB を直接直す
  - 対象者は、在籍中で学年のある、予約できる役割の人（学生と、学年のある admin）。teacher・学年の無い人・卒業生は対象にしない
  - その年度の4月1日（日本時間）以降に作られたアカウントも対象にしない。登録のときに4月時点の正しい学年を選んでいるため、更新すると1つ上がりすぎる。3月までにログインだけして4月に学年を登録した人は対象に入り、1つ上がる（作られた日時でしか見分けられないため）。次の年度からは通常どおり対象になる
  - B1〜B3・MIDS_B1〜B3・M1 は自動で1つ上がる。B4・MIDS_B4・M2 は進路（`graduate` / `continue`）をリクエストで指定し、`continue` は B4・MIDS_B4 なら M1、M2 なら M2 のまま。卒業は `isEnrolled` を `false` にし、学年は残す
  - 進路が抜けている人がいれば `409 GRADE_PROMOTION_PATH_REQUIRED` で何も更新しない（要るかどうかが今の学年で決まるため `400` にしない）。`paths` に対象外の人や自動で上がる人が入っていても無視する（画面を開いたあとに teacher へ変わった人などで、全体を止めないため）
  - 同じ年度の2回目は `409 GRADE_PROMOTION_ALREADY_EXECUTED`。1回目のあとは元の B3 が B4 になっていて進路の抜けが出るため、進路の抜けより先に判定する
  - 卒業する人の、開始前で「済」でない予約を消す（役割の変更で teacher にするときと同じ。発表の記録は残す）。卒業生が新しく予約できる点は今回変えない
  - 卒業で在籍中の admin が0人になるなら `409 LAST_ADMIN` で何も更新しない（#13 と同じ理由）。誰も卒業しないときは、admin が卒業生だけでも止めない。判定の順は、4月か → 実行済みか → 進路の抜け → 最後の admin
  - 全員の行を id の順に `FOR UPDATE` でロックしてから判定し、2回同時の実行や同時の役割の変更でも、二重に更新したり admin を0人にしたりしない。今の対象者だけでなく全員をロックするのは、学年の登録や teacher からの変更が途中で確定すると、判定のあとに対象者が増えるため。更新の途中に来た登録は更新のあとに確定するので、登録した学年のまま上がらない。記録の INSERT・予約の削除・学年の更新は `db.batch` で送り、後ろの2つは「この実行で記録が入ったとき」だけ実行する（同じ年度の2回目で INSERT が0行のときに、1回目の記録を見て更新しないように、年度ではなくこの実行の id で確かめる）。学年の更新は `CASE` の1文にする（別々の文だと B1 → B2 → B3 と2つ上がるため）
  - 操作者が admin かは入口だけで確かめる（権限そのものは変えないため）
  - 卒業した admin は役割を変えず、権限を残す。入口は役割だけを見るため、ほかの admin が外すまで管理画面を使える。admin が卒業生だけのときに、新しい admin を作って復旧できるようにするため（#13 の決定を保つ）
  - 画面（`/admin/grade-promotion`）は、進路を選ぶ人と自動で上がる人を分けて並べる。進路の初期値は空で、全員を選ぶまで実行できない。確認ダイアログに人数と元に戻せないことを書き、卒業する人がいれば予約が消えることも書く。4月以外と実行済みのときは一覧を出さない。対象者が0人のときは実行できない（年度の記録だけが残るため）

## 6. データ構造

詳細は `docs/design/db-reservation.md`（判断理由つき）と `database.dbdiagram` を参照。

```
users ──< reservations >── slots >── seminarDays
  │  └──< gradePromotions                  │
  └──────────< announcements >─────────────┘
```

| テーブル | 要点 |
|---|---|
| `users` | better-auth + `role` / `grade` / `displayName` / `isEnrolled` |
| `seminarDays` | `date` UNIQUE、`status`（open / closed）、`closedReason` |
| `slots` | `period`（3〜6）、開始・終了時刻、`kind`。UNIQUE(seminarDayId, startTime)、CHECK(`startTime < endTime`) |
| `reservations` | `slotId` UNIQUE で二重予約を防ぐ。取消は物理削除。`status`（reserved / done） |
| `announcements` | 開催日（`seminarDayId`）・書いた人（`authorId`）・本文（`body`）・表示期間（`displayFrom` / `displayUntil`、任意）。CHECK(`displayFrom <= displayUntil`) |
| `gradePromotions` | 学年更新の記録。`academicYear` UNIQUE で二重実行を防ぐ |

- 発表回数は列に持たず、`done` の予約の件数で出す
- 時間割テンプレートはコード定数（`src/shared/schedule-template.ts`。GAS の `SCHEDULE` を移植）

## 7. API 設計

| メソッド | パス | 権限 | 内容 |
|---|---|---|---|
| `*` | `/api/auth/*` | – | better-auth |
| GET | `/api/me` | ログイン済 | 自分の情報・役割・プロフィール登録済みか |
| POST | `/api/me/profile` | ログイン済 | 初回のプロフィール登録（表示名・学年）。学年が要る人（student と `@stu.` の admin）が `grade: null` を送る、または学年を持たない人（teacher と `@ds.` の admin）が学年を送ると `400`（`409` にしない理由は「2. ユーザー」）。登録済みなら `409` |
| PATCH | `/api/me/profile` | ログイン済 | 表示名の変更（学年を含むと `400`）。未登録なら `409` |
| GET | `/api/me/reservations` | ログイン済 | 自分の予約一覧 ＋ 発表回数 |
| GET | `/api/days?month=YYYY-MM` | ログイン済 | 月内の開催日・状態・休止理由・空き枠の数 |
| GET | `/api/days/next` | ログイン済 | 今日（Asia/Tokyo）以降で一番近い開催日（休止日も含む）の枠と予約者名。形は `/api/days/:date` と同じ。開催日が無ければ `200` で `{ day: null, slots: [] }` |
| GET | `/api/days/:date` | ログイン済 | その日の枠と予約者名（休止日も枠を返す）。ログイン中の人が予約できるか・取り消せるかも返す。開催日でなければ `404` |
| POST | `/api/slots/:slotId/reservations` | student / admin | 予約。埋まっている・予約できない枠なら `409`。処理の途中で teacher に変わったときも `403` |
| DELETE | `/api/reservations/:id` | 本人 / admin | 取消。本人でも開始後・「済」なら `409` |
| GET | `/api/announcements?current` | ログイン済 | 表示期間中の全体連絡 |
| GET | `/api/announcements/upcoming` | ログイン済 | 編集できる、表示前の全体連絡（teacher は自分の分、admin は全員分） |
| POST | `/api/announcements` | teacher / admin | 全体連絡の作成。開催日でない日付なら `404 SEMINAR_DAY_NOT_FOUND` |
| PATCH / DELETE | `/api/announcements/:id` | 書いた本人 / admin | 編集・削除。他人の連絡なら `403`、連絡が無ければ `404 ANNOUNCEMENT_NOT_FOUND`、（PATCH で）開催日でない日付なら `404 SEMINAR_DAY_NOT_FOUND` |
| GET | `/api/stats/presentations` | teacher / admin | 全員の発表回数 |
| GET | `/api/admin/grade-promotions` | admin | 今の年度の実行状況（年度・実行できる期間か・実行済みの情報）と対象者の一覧 |
| POST | `/api/admin/grade-promotions` | admin | 学年更新（卒業する人の開始前の予約を削除）。4月以外は `409 GRADE_PROMOTION_NOT_OPEN`、同じ年度は `409 GRADE_PROMOTION_ALREADY_EXECUTED`、進路の抜けは `409 GRADE_PROMOTION_PATH_REQUIRED`、在籍中の admin が0人になるなら `409 LAST_ADMIN` |
| PATCH | `/api/admin/days/:date` | admin | 休止・再開と理由（行が無ければ作る。休止時は開始前の枠の予約を削除）。金曜以外は `400`、今日より前は `409 SEMINAR_DAY_PAST` |
| PATCH | `/api/admin/slots/:id` | admin | 枠の種類・開始時刻・終了時刻の編集（`presentation` から `presentation` 以外にしたら予約を削除）。枠が無ければ `404 SLOT_NOT_FOUND`、開始時刻を過ぎた枠は `409 SLOT_STARTED`、同じ日に同じ開始時刻の枠があれば `409 SLOT_START_TIME_TAKEN`、画面で見ていた変更前の値が今の枠と違えば `409 SLOT_CHANGED` |
| GET | `/api/admin/users` | admin | 利用者一覧（表示名・メール・学年・役割・在籍中か） |
| PATCH | `/api/admin/users/:id` | admin | 役割の変更（teacher にしたら学年を `null` にし、開始前の予約を削除）。入口を通ったあとに操作者が外されていたら `403 FORBIDDEN`、利用者がいなければ `404 USER_NOT_FOUND`、在籍中の admin が0人になる変更は `409 LAST_ADMIN`、学年の無い人を学年なしで student にすると `409 GRADE_REQUIRED` |
| (Cron) | `scheduled` | – | 今日（Asia/Tokyo）以降の金曜を4回分、冪等に生成 / 過ぎた予約を `done` にする |

- フロントからは Hono RPC クライアントで呼び出す
- 入力検証は zod（`src/shared/schemas.ts`）
- 成功は `200`（作成も含む）、競合は `409`、権限不足は `403`、エラーは `{ error: { code, message } }`（`docs/conventions/api.md`）
